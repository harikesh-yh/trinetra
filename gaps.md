# TRINETRA — Honest Gap List

What is **NOT yet built** in this prototype versus the full winning plan, so the team knows
exactly what remains. The prototype is a complete, working *local* system (FastAPI + SQLite +
React/Vite) with all engine modules and the trust spine functioning end-to-end on synthetic
data. The gaps below are the distance from that to the full, deployed, submission-winning
product.

Organized by priority: **must-have for a valid/strong submission** vs **nice-to-have**.

---

## A. Must-have for submission

### A1. Catalyst deployment not done (BLOCKER for a valid submission)
The platform currently runs locally as **FastAPI + SQLite + Vite**. The KSP Datathon requires a
**live deployment exclusively on Zoho Catalyst**. Nothing is deployed yet. The full migration is
mapped service-by-service in [`trinetra/CATALYST_MAPPING.md`](trinetra/CATALYST_MAPPING.md):
- FIR + AuditLog → **Data Store** (replace SQLite).
- Engine modules → **Functions**; heavy graph/ML → **AppSail**.
- Front-ends → **Slate / Web Client Hosting**.
- **API Gateway + Authentication** in front of the engine.
- QuickML / Zia AutoML / Zia Services / SmartBrowz / Stratus / Cache / Cron / Signals / Pipelines.
This is the single biggest remaining item and gates the **Deployed Link** deliverable.

### A2. Demo video + filled live deployed link still needed
Two official submission artifacts are still outstanding:
- **Demo video** (public Drive / unlisted YouTube) — not recorded.
- **Deployed link** — pending the Catalyst deployment in A1.
Both are `[PLACEHOLDER]` in the submission template until produced.

### A3. Real FIR data not integrated
All 4000 FIRs are **synthetic** (generated by `generate_data.py` on the real KSP ER schema, with
planted demo structures). KSP has released the schema only, not rows. **Action:** when KSP
releases real data, load it into the same schema (Data Store) — the engine is schema-driven and
should need little change. Demo facts (Koramangala/Whitefield/Electronic City/Indiranagar) are
synthetic and will disappear with real data.

### A4. No real Authentication / RBAC backend
Login is a **demo role switch** between three hard-coded users (`rbac.py` `DEMO_USERS`). RBAC
scope (`WHERE` injection by role) *is* enforced in the engine and is auditable, but there is no
real identity provider, password/SSO, session management, or per-user provisioning. **Action:**
wire **Catalyst Authentication** and map real officer identities → scope.

## B. High-value (strongly improves the demo / score)

### B1. NL is deterministic intent-based, not a true LLM
`text2sql.py` / `router.py` use deterministic **intent matching + templated, whitelisted SQL**,
not a real LLM Text→SQL. This is safe and fully offline, but only covers the anticipated question
space. An optional `OPENAI_API_KEY` path is **stubbed but not implemented**. **Action:** real
Text→SQL LLM served via **QuickML**, keeping the same safety rails (read-only, whitelist,
row-limit, RBAC `WHERE`, cite/explain).

### B2. Kannada is static, not real Zia
Kannada support is **static i18n strings + a phrase map + the browser Web Speech API** for
voice — not real speech-to-text / text-to-speech / translation. **Action:** **Zia Services** for
Kannada STT/TTS/translate (and OCR for scanned FIRs).

### B3. Forecast is moving-average / linear-trend, not Prophet/LightGBM
`hotspot.py` forecasting uses a **moving-average / linear-trend** heuristic. The plan calls for
**Prophet / STL or LightGBM** spatio-temporal models. The current output is plausible and demos
well but is not a tuned model. **Action:** train proper models (on AppSail / Zia AutoML).

### B4. RAG is keyword/embedding stand-in, not a vector DB
`rag.py` does similarity over `BriefFacts` with a lightweight in-process approach, not a true
vector index. **Action:** **QuickML** vector store for semantic "similar MO" search.

## C. Nice-to-have / polish

### C1. No Cron proactive briefings
Scheduled station digests (new hotspots, active repeat offenders, anomalies) via **Cron →
Mail/Push** are **not wired**. Step 9 of the plan's demo (sample proactive email) is not built.

### C2. No Signals auto-anomaly on new FIRs
The anomaly scan is a **manual endpoint**; there is no **Signals + Event Functions** trigger that
auto-runs anomaly detection when a new FIR lands.

### C3. Tests are smoke-level, not comprehensive
`tests/test_engine.py` is **13 smoke checks** (all passing) that verify the planted demo facts and
the trust spine (RBAC scope, citations, disclaimers). There is no broad unit-test suite, no
frontend tests, no CI. **Action:** expand coverage + add **Pipelines** CI.

### C4. Risk score is a heuristic, not Zia AutoML
`risk.py` composes a weighted heuristic score, not a trained **Zia AutoML** tabular model.

### C5. Other honest gaps observed
- **No persistence of audit across restarts beyond the SQLite file** — fine locally, but Data
  Store is the production target.
- **CORS is wide open** (`allow_origins=["*"]`) for local dev — lock down in prod.
- **No rate limiting / throttling** — comes free with **API Gateway** in prod.
- **PDF brief** is functional but minimally styled — SmartBrowz can produce richer reports.
- **No mobile / responsive polish** — the War Room is desktop-first.
- **Map tiles + graph physics** can be heavy on low-end machines (caused screenshot timeouts).

---

## Summary

The **engine and trust spine are real and working**; the gaps are concentrated in (1) **Catalyst
deployment**, (2) **real data**, (3) **swapping deterministic stand-ins for real ML/LLM/voice
services**, and (4) the two outstanding submission artifacts (**demo video + deployed link**).
The architecture was deliberately built so each stand-in maps 1:1 to a Catalyst service (see
[`trinetra/CATALYST_MAPPING.md`](trinetra/CATALYST_MAPPING.md)), so closing these gaps is
migration work, not a rewrite.
